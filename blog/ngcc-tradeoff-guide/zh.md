# 怎么看 NGCC Explorer 的 Trade-off Layer

*约 5 分钟阅读 · 2026 年 10 月 22 日*

[NGCC Explorer](../../ngcc-explorer/) 把每条测试结果画成一个点。Trade-off analysis 要回答的问题很具体：**在可比较的结果中，有没有另一条结果在当前选定的两个指标上都不差，并且至少一项更好？** 它只回答这个问题，不给算法打综合分。

## “两个指标”到底是哪两个？

就是图上方选定的 **X axis 和 Y axis**。默认值如下：

| 页面 | 横轴 X | 纵轴 Y |
| --- | --- | --- |
| KEM | 公钥 + 密文大小，单位为字节 | 解封装耗时，单位为 CPU cycles |
| Signature | 签名大小，单位为字节 | 验证耗时，单位为 CPU cycles |

两个轴都可以切换。例如，把解封装耗时改成封装耗时，问的就是另一个问题，Layer 也可能随之改变。默认轴只是展示“通信大小与计算耗时”取舍的一个起点，并不是说其他成本不重要。这里两个指标都按**越小越好**来比较。

## 什么叫“比当前结果更好”？

假设当前行是 **1,000 字节、1.1 亿 cycles**。另一条结果是 **900 字节、1 亿 cycles**：它更小也更快，因此在这两个指标上优于当前行。如果另一条是 **900 字节、1.2 亿 cycles**，它虽然更小，却更慢；这就是取舍，不能说它在这两个指标上明确更好。

表格里 “Better on these two metrics” 后列出的算法和参数集，符合上述严格条件。点击当前行，还能看到它们各自的 X/Y 数值。这里的“更好”**只针对当前两项数字和筛选范围**，不代表安全性、实现质量或实际部署效果一定更好。

## Layer 1、Layer 2、Layer 3 怎么分？

假设下面四条虚构结果属于同一个可比较的组：

| 结果 | 大小（字节） | 耗时（百万 cycles） | Layer |
| --- | ---: | ---: | ---: |
| A | 900 | 100 | 1 |
| B | 800 | 120 | 1 |
| C | 1,000 | 110 | 2 |
| D | 1,100 | 130 | 3 |

A 比 B 快，B 比 A 小，谁也不能在两项上同时胜出，所以 **A、B 都是 Layer 1**。A 比 C 更小、更快，因此 C 不在第一层。先移除 A、B，再看剩下的结果：C 没有更优替代，所以 **C 是 Layer 2**。再移除 C，**D 是 Layer 3**。

Layer 1 就是这两个指标下的 *Pareto frontier*（帕累托前沿）；后续层是在移除前一层后重复寻找前沿。蓝色只是突出 Layer 1。**同一层没有先后名次**：Layer 1 不等于“最好的算法”，Layer 2 也不等于“第二名”。

## 哪些结果会放在一起比较？

网站只比较**当前筛选后可见**、且声称安全强度处于同一个 128/256/512-bit 组、机器、实现版本、构建配置和编译参数都相同的结果。192-bit 和 384-bit 变体不参与这项比较。缺少任一轴的数据、没有比较组，或相关已知答案测试未通过的结果会显示为 *Unranked*。

因此，切换方案筛选条件、机器、实现或坐标轴，都可能改变 Layer。不同机器上的 CPU cycles 也不能直接混成一个速度排行榜。有关大小、耗时和安全分组的原始来源与处理规则，可查看项目的 [Data and methods](https://github.com/zhengjieyu/ngcc-benchmark-explorer/blob/main/docs/DATA_AND_METHODS.md)。

想看真实记录的对比，可以继续读 [NGCC Explorer 数据观察](../ngcc-explorer-report/?lang=zh)。
